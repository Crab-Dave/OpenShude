# 身份与权限设计

## 1. 设计目标

系统采用“基础身份 + 管理员组授权 + 数据范围”的权限模型，满足以下要求：

- 系统初始化时创建超级管理员。
- 正式账号导入后默认都是普通用户，不自动获得管理权限。
- 超级管理员可以把普通用户加入一个或多个管理员组。
- 每个管理员组独立配置管理权限和可管理的年级范围。
- 管理员只能操作其授权范围内的用户、卡片、举报和宿舍。
- 权限模型可以在未来扩展到选宿舍批次或楼栋等范围。

权限控制必须在后端执行。前端隐藏菜单或按钮只能改善使用体验，不能作为安全措施。

## 2. 身份定义

### 2.1 超级管理员 `SUPER_ADMIN`

超级管理员是全局身份，不受管理员组数据范围限制，负责：

- 创建、修改、停用管理员组。
- 配置管理员组的权限和数据范围。
- 添加或移除管理员组成员。
- 管理管理员账号本身。
- 执行全局配置、高风险删除和跨范围处置。
- 查看完整的管理审计日志。

系统必须始终至少保留一个可登录的超级管理员。最后一个有效超级管理员不能被停用、删除或降级。

### 2.2 管理员组成员 `GROUP_ADMIN`

管理员组成员不是独立的账号类型，而是“普通用户账号 + 至少一个有效管理员组成员关系”。因此同一账号可以继续使用普通用户功能，同时进入管理工作台。

管理员的有效授权来自其所属的有效管理员组。加入多个组时，各组授权可以叠加，但每次操作必须由同一个组同时满足权限和数据范围，不能把不同组的权限与范围交叉组合。

例如：

- A 组拥有“修改身份信息”权限，只管理 2026 级。
- B 组拥有“查看宿舍”权限，只管理 2025 级。
- 该管理员可以修改 2026 级身份信息、查看 2025 级宿舍。
- 该管理员不能修改 2025 级身份信息。

### 2.3 普通用户 `USER`

导入账号时默认创建为普通用户。普通用户只能使用学生侧功能，并受资源所有权、会话参与关系、性别、轮次参与名单、宿舍成员关系和选宿舍轮次状态约束。

## 3. 授权原则

1. **默认拒绝**：没有明确授权的操作一律拒绝。
2. **最小权限**：管理员组只授予完成职责所需的权限。
3. **权限与范围同时校验**：管理操作必须同时具备操作权限和目标资源范围。
4. **同组匹配**：至少有一个有效管理员组同时包含所需权限并覆盖目标资源，操作才被允许。
5. **服务端可信**：角色、管理员组、目标年级和资源归属均从数据库读取，不接受客户端声明。
6. **字段级保护**：能够查看用户不代表能够修改身份、状态或永久删除用户。
7. **关系级保护**：私信仅对会话参与者可见；宿舍成员管理仅对该宿舍发起人开放。
8. **状态级保护**：账号状态、卡片状态、宿舍状态和选宿舍轮次状态会进一步限制操作。
9. **管理操作留痕**：所有管理写操作和敏感导出都必须写入审计日志。

## 4. 管理员组

管理员组至少包含：

- 唯一编码、名称和说明。
- 状态：`ACTIVE` 或 `DISABLED`。
- 权限集合。
- 数据范围集合。
- 创建人、创建时间和更新时间。

停用管理员组后，其全部授权立即失效，但组、成员关系和历史审计记录继续保留。

### 4.1 数据范围

第一阶段只启用 `GRADE` 年级范围。年级必须使用稳定的年级 ID 或编码，不能直接依赖可修改的展示文本。

范围结构应保留扩展能力：

| 范围类型 | 示例 | 当前状态 |
|---|---|---|
| `GRADE` | 2026 级 | 启用 |
| `DORMITORY_ROUND` | 2026 新生第二轮 | 预留 |
| `BUILDING` | 学生宿舍 11 栋 | 预留 |

新增范围类型时必须为对应资源定义明确的归属规则，不能仅增加一个字符串类型后直接用于授权。

### 4.2 资源范围判断

- 用户、室友卡片、举报：以目标用户的年级为准。
- 宿舍：建议增加不可由普通用户修改的 `management_grade_id`，创建宿舍时从发起人年级写入。
- 宿舍成员身份修改：仍按该成员自己的年级单独校验，不能因为管理员有权管理宿舍就获得管理全部成员账号的权限。
- 跨年级宿舍：对宿舍整体操作按 `management_grade_id` 授权；涉及具体成员的操作按成员年级再次授权。未来若跨年级成为常态，应改为选宿舍批次范围，而不是推断成员年级。
- 选宿舍轮次配置、全局设置、管理员组、全局审计日志：不属于任何年级范围，只允许超级管理员操作。

## 5. 权限项

权限编码由后端维护固定白名单，管理员组只能从白名单中选择，不能创建任意权限字符串。

| 权限编码 | 含义 | 数据范围 | 默认建议 |
|---|---|---|---|
| `USER_READ` | 查看用户身份、状态和卡片状态 | 年级 | 年级管理员 |
| `USER_IMPORT` | 导入普通用户 | 导入行的年级 | 受信任的账号管理员 |
| `USER_LOGIN_IDENTIFIER_UPDATE` | 批量修改登录标识 | 目标用户年级 | 受信任的账号管理员 |
| `USER_IDENTITY_UPDATE` | 修改姓名、年级、性别、专业 | 目标用户年级；修改年级时还需覆盖新年级 | 年级管理员 |
| `USER_STATUS_UPDATE` | 停用、启用或封禁普通用户 | 目标用户年级 | 年级管理员 |
| `CARD_READ` | 在治理后台查看卡片 | 持卡人年级 | 内容管理员 |
| `CARD_MODERATE` | 隐藏或恢复卡片 | 持卡人年级 | 内容管理员 |
| `DORMITORY_READ` | 查看宿舍和成员 | 宿舍管理年级 | 宿舍管理员 |
| `DORMITORY_LOCATION_ASSIGN` | 分配楼栋和房间号 | 宿舍管理年级 | 宿舍管理员 |
| `DORMITORY_CLOSE` | 关闭异常宿舍 | 宿舍管理年级 | 高级宿舍管理员 |
| `DORMITORY_EXPORT` | 导出宿舍列表 | 仅导出授权年级 | 宿舍管理员 |
| `REPORT_READ` | 查看举报及其快照 | 被举报对象所属年级 | 内容管理员 |
| `REPORT_RESOLVE` | 处理举报 | 被举报对象所属年级 | 内容管理员 |
| `AUDIT_READ_SCOPED` | 查看授权范围内的管理日志 | 日志目标年级 | 管理组负责人 |

以下权限不下放到普通管理员组，只允许超级管理员执行：

- 管理管理员组、权限、范围和组成员。
- 修改或停用具有管理权限的账号。
- 永久删除账号及其资源。
- 创建、配置、开放、截止或归档选宿舍轮次。
- 创建、修改或删除用于批量选人的预设学生群组。
- 查看全局审计日志。
- 执行跨范围管理操作。

如果未来需要下放上述权限，应新增独立权限编码和审批规则，不能复用宽泛的“管理员”判断。

## 6. 普通用户的资源级权限

### 6.1 账号

- 可以查看自己的账号和身份字段。
- 可以修改自己的密码。
- 不能修改姓名、年级、性别、专业和登录标识。
- 不能自行注销或删除账号；账号状态和永久删除由管理员处理。
- 不能查看其他用户的登录标识、账号状态或管理信息。
- 管理员批量修改登录标识后，旧标识立即失效，用户必须使用新标识重新登录。
- 尚未完成首次改密的账号会同步将一次性密码更新为新登录标识；已经自行设置的密码保持不变。

### 6.2 室友卡片

- 只能创建和修改自己的卡片。
- 卡片首次发布后不能取消发布，只能继续更新。
- 只能查看正常账号已发布且未被隐藏的卡片。
- 被任一方拉黑后，双方不能查看对方卡片或发起私信。
- 举报卡片时只保存必要快照，不向举报人暴露额外信息。

### 6.3 私信

- 只有会话双方可以查看消息、发送消息和更新已读状态。
- 普通管理员和超级管理员均不能通过管理后台浏览完整私信内容。
- 举报私信时，管理员只能看到举报时生成的必要快照及处理信息。
- 如未来因安全事件需要调取完整私信，应设计独立的高风险审批和审计流程。

### 6.4 宿舍

- 选宿舍轮次包含 `DRAFT`、`OPEN`、`CLOSED`、`ARCHIVED` 四种状态，状态只允许按此前后顺序流转，同一时间最多有一个 `OPEN` 轮次。
- 超级管理员在草稿状态配置明确的参与学生名单；只有名单内用户能参与该轮选宿舍。
- 轮次开放时，参与用户才能创建、申请加入、审核申请、移除成员或退出宿舍。
- 用户在同一轮次最多加入一个宿舍；可以在不同轮次分别加入宿舍，旧轮次成员关系不得阻止其参加新轮次。
- 用户只能申请加入同性别且未满员的宿舍。
- 只有宿舍发起人可以审核加入申请和移除本宿舍的其他成员。
- 发起人不能通过移除成员接口移除自己，只能主动退出。
- 宿舍为空时自动删除；发起人退出后由最早加入的成员继任。
- 轮次截止后所有用户侧宿舍变更操作停止，管理员仍可检查宿舍并分配楼栋和房间号。
- 轮次归档时生成宿舍与成员文本快照，之后禁止修改该轮宿舍。快照保留姓名、登录标识、年级、性别和专业等必要结果字段，源账号永久删除后仍可查询。
- 新轮次创建独立的宿舍、成员和申请记录，不复用或清空旧轮次数据。

### 6.5 人员搜索与预设学生群组

- 所有人员候选列表和人员查看列表均应提供按姓名搜索；搜索只缩小当前显示范围，不改变已经勾选的人员。
- 超级管理员可以创建、修改和删除预设学生群组，群组成员只能是有效普通学生账号。
- 预设学生群组与管理员权限组是两类独立资源：前者只保存可复用的学生名单，后者负责授权。
- 在轮次参与人或管理员组成员配置中使用预设群组时，系统将群组成员追加到当前勾选结果，不取消原有选择。
- 一键添加是使用时的名单复制。以后修改或删除预设群组，不得改变已经保存的轮次参与名单或管理员组成员。

## 7. 管理目标保护

- 组管理员不能通过管理接口修改自己的身份、状态或管理员组关系。
- 组管理员不能停用、封禁、删除或修改任何具有有效管理员组成员关系的账号。
- 只有超级管理员能管理其他管理员；最后一个超级管理员受到额外保护。
- 永久删除必须要求再次输入目标登录标识和操作原因。
- 修改用户年级时，执行授权的同一个管理员组必须同时覆盖原年级和目标年级，避免借修改年级绕过范围控制。
- 批量导入必须逐行授权；某一行超出范围不应导致已通过校验的其他行越权写入，返回结果需逐行说明成功或失败。
- 批量修改登录标识必须整批校验、整批提交；原标识不存在、新标识重复或任一目标超出授权范围时整批不修改。
- 登录标识修改不改变内部用户 ID 或业务资源关联，也不改写已经归档的宿舍结果快照。

## 8. 账号和授权状态

账号状态继续使用：

- `PENDING_ACTIVATION`：已导入但未首次登录。
- `ACTIVE`：正常使用。
- `SUSPENDED`：临时停用。
- `BANNED`：封禁。

只有 `ACTIVE` 和按现有激活流程允许的 `PENDING_ACTIVATION` 可以登录。账号进入其他状态后，应立即删除其全部会话。

管理员组、成员关系、权限或范围发生变化后，授权必须立即生效。实现时可以在每次管理请求中查询有效授权；如使用缓存或会话声明，必须维护 `authorization_version` 并在变更时使旧授权失效。

## 9. 建议数据模型

### 9.1 用户

`users` 保留全局身份字段：

- `account_type`: `USER` 或 `SUPER_ADMIN`。
- `authorization_version`: 权限变更版本号。
- 现有姓名、年级、性别、专业、账号状态等字段。

不建议继续使用单一的 `ADMIN` 值表达组管理员，因为它无法描述多个管理员组和不同数据范围。

### 9.2 管理员组相关表

- `admin_groups(id, code, name, description, status, created_by, created_at, updated_at)`
- `admin_group_members(group_id, user_id, created_by, created_at)`
- `admin_group_permissions(group_id, permission_code, created_by, created_at)`
- `admin_group_scopes(group_id, scope_type, scope_value, created_by, created_at)`

必要约束：

- 组编码唯一。
- 组成员、组权限和组范围分别设置联合唯一约束。
- 外键删除采用明确策略；建议停用组而不是直接删除。
- 只有 `USER` 可以加入管理员组，超级管理员不需要组授权。
- `permission_code` 和 `scope_type` 写入前必须通过后端白名单校验。

### 9.3 资源归属和审计

- 年级应逐步规范为稳定 ID，展示名称可以单独修改。
- `dormitories` 增加 `management_grade_id`，创建后仅超级管理员可以更正。
- 审计日志增加 `permission_code`、`grant_group_id`、`scope_type`、`scope_value`、`request_id`、操作结果以及变更前后快照。

## 10. 后端鉴权流程

每个受保护请求按以下顺序处理：

1. 验证会话、CSRF 和账号状态。
2. 判断是否为普通用户自助操作，并校验资源所有权或参与关系。
3. 管理操作声明唯一的权限编码。
4. 从数据库读取目标资源及其管理范围。
5. 超级管理员直接通过权限层，但仍继续执行业务状态校验和审计。
6. 对组管理员，查找是否存在一个有效组同时授予该权限并覆盖目标范围。
7. 校验字段级限制、目标账号保护和业务状态。
8. 在事务内完成写入并记录审计日志。

缺少权限时返回 `403`。为避免枚举越权资源，当管理员有对应功能权限但目标不在其范围内时，可以统一返回 `404`。批量接口必须对每个目标单独执行范围校验。

接口不应使用 `requireAdmin()` 这类只判断单一角色的宽泛入口作为最终授权。应改为类似以下语义的检查：

```text
authorize(actor, permissionCode, resourceScope, target)
```

该检查必须返回实际命中的超级管理员身份或管理员组授权，供审计日志记录。

## 11. 审计和隐私

以下操作必须记录成功和失败结果：

- 管理员组、成员、权限和范围变更。
- 用户导入、登录标识修改、身份修改、状态修改和永久删除。
- 卡片隐藏或恢复、举报处理。
- 宿舍位置分配、关闭和导出。
- 选宿舍轮次的创建、配置、开放、截止和归档。
- 预设学生群组的创建、成员调整和删除。
- 被拒绝的高风险越权尝试。

审计记录至少包含：操作者、命中的授权组、权限编码、数据范围、目标、原因、变更前后摘要、IP、User-Agent、请求 ID、时间和结果。审计日志不能由普通管理员修改或删除。

管理接口遵循数据最小化：

- 用户列表不返回密码信息、会话令牌或无关隐私字段。
- 宿舍导出只包含管理员授权范围内的数据。
- 举报后台只展示举报快照，不提供任意私信检索能力。
- 操作超出范围时，不在错误信息中泄露目标用户或宿舍是否存在。

## 12. 前端行为

- 普通用户加入管理员组后，可以在学生端与管理工作台之间切换。
- 管理菜单按有效权限显示；没有写权限时可以只读展示或隐藏操作按钮。
- 年级筛选器只能选择管理员实际有权管理的范围。
- 前端收到 `403` 时提示权限不足，收到范围隐藏的 `404` 时按资源不存在处理。
- 权限在使用过程中被回收时，下一次请求必须失败并刷新管理菜单。

## 13. 初始化和迁移建议

1. 先备份数据库并完成恢复演练。
2. 新增目标权限表、约束和索引。
3. 将当前系统管理员迁移为 `SUPER_ADMIN`，其他账号迁移为 `USER`。
4. 为已有年级建立稳定编码并回填用户及宿舍管理范围。
5. 写入固定权限白名单。
6. 将管理接口逐个替换为权限编码和资源范围鉴权；同一次发布完成切换，不长期保留新旧两套授权路径。
7. 验证至少存在一个有效超级管理员后，再移除旧的 `ADMIN` 角色判断。

生产环境初始化超级管理员时不得使用仓库内硬编码的默认密码。应通过部署密钥提供一次性强密码，并要求首次登录后修改。

## 14. 验收测试

至少覆盖以下场景：

- 导入账号默认为普通用户，无管理权限。
- 一个用户加入多个管理员组后，只能使用同组内匹配的权限和范围。
- 管理员可以操作授权年级，不能操作未授权年级。
- 修改年级时必须同时覆盖原年级和目标年级。
- 管理员不能管理自己或其他管理员账号。
- 停用组、移除组成员或撤销权限后立即失效。
- 宿舍列表、详情、位置分配、关闭和导出均按范围过滤。
- 满员宿舍仍可被有权限的管理员查看和管理。
- 管理员不能读取普通用户的完整私信。
- 选宿舍轮次管理、管理员组管理和永久删除仅超级管理员可用。
- 同一批学生可参加两轮选宿舍，每轮仍只能加入一个宿舍，第一轮归档结果不受第二轮操作影响。
- 非本轮参与学生不能创建宿舍或发送加入申请，同时不能开放两个轮次。
- 截止后学生不能变更宿舍；归档后管理员不能修改宿舍，按轮次导出只包含该轮数据。
- 归档结果在源用户永久删除后仍保留必要的姓名和登录标识快照。
- 人员候选列表可以按姓名过滤，使用预设群组能一次添加全部有效成员，且不会覆盖原有勾选。
- 修改或删除预设群组不影响已经保存的轮次参与人及管理员组成员。
- 最后一个超级管理员不能被停用、删除或降级。
- 所有管理写操作和敏感导出均产生包含授权来源的审计日志。
- 伪造角色、组 ID、年级或目标 ID 不能绕过后端校验。
