# “宿得道理”页面设计

## 1. 背景与目标

“宿得道理”用于新生在学校正式确认住宿安排后，共同建设和展示自己的宿舍空间。它包含两类场景：

- **我的宿舍**：查看自己所属的正式宿舍，维护宿舍昵称、简介和公约，查看舍友卡片，以及转让宿舍长身份。
- **赛博串门**：浏览其他正式宿舍及其公开内容，但不能修改不属于自己的宿舍。

这里的“正式宿舍”由管理员按学校最终名单导入，与自由选宿舍阶段产生的组队宿舍完全独立。自由选宿舍结果不会自动生成、覆盖或同步正式宿舍；如需以选宿舍结果制作正式名单，应先由管理员在线下确认，再按本设计导入。

一期不实现成员自主加入或退出、访客留言、宿舍动态、点赞、附件上传、图片 Markdown、宿舍间私信和“后花园”静态主页。“后花园”只保留不可点击或标明“建设中”的入口。

## 2. 术语与参与者

### 2.1 术语

- **组队宿舍**：自由选宿舍轮次中的临时组队结果，继续使用现有 `dormitories`、`dormitory_members` 等数据。
- **正式宿舍**：管理员依据学校名单导入的最终住宿关系，使用独立的 `official_dormitories` 和 `official_dormitory_members` 数据。
- **宿舍编号**：由管理员导入的稳定编号，例如 `1023`。成员不可修改。
- **宿舍昵称**：成员共同维护的自定义字段，例如“四驱兄弟”。页面名称按“宿舍编号·宿舍昵称”组合展示；昵称为空时只显示宿舍编号。
- **宿舍长**：导入行中的第一位成员。每个正式宿舍必须且只能有一名宿舍长。
- **管理年级**：正式宿舍导入时由成员年级确定的权限范围，不向普通用户开放修改。

### 2.2 参与者

- **普通学生**：状态正常的已登录普通账号。可以浏览“赛博串门”，并按自己的正式成员关系使用“我的宿舍”。
- **宿舍成员**：属于某个正式宿舍的普通学生。可以共同修改该宿舍的昵称、简介和公约。
- **宿舍长**：除普通成员能力外，可以把宿舍长身份转让给同一宿舍中的另一名有效成员。宿舍长不能增删正式成员。
- **正式宿舍管理员**：通过有效管理员组获得相应权限，且同一管理员组覆盖宿舍管理年级的管理员。
- **超级管理员**：直接通过权限层，但仍必须通过导入校验、业务约束、确认和审计流程。

管理员组成员使用学生端时遵循普通学生的资源关系；拥有管理权限不等于自动成为宿舍成员，也不能从学生端修改任意宿舍。

## 3. 页面、路由与导航

### 3.1 入口与登录

- 首页顶栏增加“宿得道理”入口，建议路由为 `/sude`。
- 未登录用户可以看到入口，但访问 `/sude` 时重定向到 `/login?next=/sude`。
- 只有状态正常的已登录账号可以进入页面。停用或封禁账号不得继续读取宿舍内容。
- 登录后默认打开“我的宿舍”；没有正式宿舍的用户看到明确空状态，并可以切换到“赛博串门”。

### 3.2 页面结构

“宿得道理”使用独立的系统标题和二级导航：

1. **我的宿舍**：展示当前用户所属的全部正式宿舍。
2. **赛博串门**：分页展示当前可访问的正式宿舍。

用户属于多个正式宿舍时，“我的宿舍”顶部提供切换器。默认选择规则依次为：上次在本设备选择的宿舍、最近加入的宿舍、宿舍 ID 最小的宿舍。本地记录只保存宿舍 ID，后端仍需重新校验成员关系。

浏览器刷新和直接访问详情时应保留当前宿舍，例如 `/sude/dormitories/{id}`。无权访问或资源不存在时不泄露差异，统一显示“宿舍不存在或暂不可访问”。

## 4. 正式宿舍与组队宿舍的隔离

正式宿舍不得复用现有组队宿舍的以下概念：

- 不属于任何自由选宿舍轮次；
- 没有 `DRAFT / OPEN / CLOSED / ARCHIVED` 选宿舍阶段；
- 没有加入申请、发起人、审批、主动退出或空宿舍自动删除；
- 不受“每名学生每轮只能加入一个宿舍”的限制；
- 不从组队宿舍的楼栋、房间、成员或归档快照自动同步数据。

同一学生可以属于多个正式宿舍，满足历史安排、跨校区安排或其他校方确认的特殊情况。同一学生在同一正式宿舍中只能出现一次。

一期正式宿舍容量仍按四人间设计，每行允许导入 1–4 名成员，以兼容暂未住满的正式宿舍。若以后需要其他容量，应增加显式容量字段和迁移，不能仅放宽数组长度。

## 5. 管理员导入

### 5.1 文件格式

一期只接收 `.xlsx` 文件，不接收带宏的工作簿、旧版 `.xls`、压缩包或外部 URL。读取第一个工作表，第一行为固定表头：

| 宿舍编号 | 成员1登录标识（宿舍长） | 成员2登录标识 | 成员3登录标识 | 成员4登录标识 |
|---|---|---|---|---|
| 1023 | 2026001 | 2026002 | 2026003 | 2026004 |

导入值全部按文本读取。登录标识和宿舍编号前后的空白会被去除，但不得把数字自动转成科学计数法、丢失前导零或计算公式。包含公式、错误单元格、隐藏外链或超出模板的成员列时拒绝该行。

限制建议：文件不超过 2 MiB、数据不超过 2000 行、宿舍编号 1–40 个字符。编号只允许中文、英文字母、数字、短横线和下划线，不允许路径分隔符、控制字符或作为公式前缀的 `= + - @`。

### 5.2 行级校验

每行必须满足：

- 宿舍编号和第一位成员均非空；成员从左到右连续填写，不能跳过中间成员列；
- 宿舍编号在文件内唯一；同一登录标识在一行内不重复；
- 所有成员均对应已有的普通学生账号，账号状态为 `PENDING_ACTIVATION` 或 `ACTIVE`；
- 所有成员属于同一年级，一期由该年级写入 `management_grade_id`；
- 执行导入的同一个有效管理员组同时具有导入权限并覆盖该年级；
- 每个宿舍不超过四人，成员 1 被设置为唯一宿舍长。

同一个学生出现在不同宿舍行中是允许的，因为产品明确支持一个学生属于多个正式宿舍。跨年级正式宿舍一期拒绝导入；未来若确有需求，应在模板中增加显式管理范围，而不是任意取其中一名成员的年级。

### 5.3 预检、确认与幂等

导入采用“预检—确认”两步：

1. 用户选择文件后，后端完整解析并返回文件 SHA-256、有效行、错误行、将创建的宿舍数和跳过数，不写数据库。
2. 管理员确认时浏览器重新提交同一文件及预检返回的哈希；哈希不一致则要求重新预检。
3. 后端再次执行全部权限和业务校验，并在一个事务中写入。任一行失败则整批不写入。

已有相同宿舍编号时：

- 编号、成员和宿舍长完全一致：视为幂等重试并跳过；
- 任一成员或宿舍长不同：拒绝整批导入，不隐式覆盖现有关系。

成员名单纠错使用单独的“修改正式成员”操作，并要求重新输入完整成员顺序、填写原因和再次确认。不能通过重复导入静默替换。删除误导入的正式宿舍属于高风险操作，只允许超级管理员在输入宿舍编号和原因后执行。

### 5.4 并发导入

- 宿舍编号使用数据库唯一约束，不能只依赖预检。
- 确认导入时开启写事务；SQLite 环境应使用现有写入串行化策略，并对锁冲突返回可重试错误。
- 两个管理员同时导入相同编号时只能有一个事务成功；另一个返回冲突，不产生部分数据。
- 导入、成员纠错和宿舍长转让之间必须串行校验，提交后仍满足“恰好一名宿舍长”。

## 6. 我的宿舍

### 6.1 信息布局

“我的宿舍”包含：

- 组合名称：`宿舍编号·宿舍昵称`；
- 宿舍简介卡片；
- 宿舍公约卡片；
- 全部正式成员的卡片区域；
- “后花园”建设中入口。

简介和公约卡片在概览中显示服务端生成的纯文本摘要，点击后打开完整 Markdown 内容。两者为空时显示引导文案，不展示伪造的默认内容。

### 6.2 共同编辑

宿舍所有当前成员均可修改：

- 宿舍昵称：纯文本，0–20 个字符；不能包含换行、控制字符或组合分隔符 `·`；
- 宿舍简介：Markdown 原文，0–2000 个字符；
- 宿舍公约：Markdown 原文，0–5000 个字符。

三个字段可以单独更新。编辑接口必须以数据库中的正式成员关系鉴权，不能信任前端传入的 `canEdit`。管理员如果不是成员，只能通过内容治理入口处理违规内容，不能假扮成员日常编辑。

前端提交时携带 `version`。后端以乐观锁更新；版本已变化时返回 `409 DORMITORY_CONTENT_CONFLICT`，保留用户输入并提示重新载入后再提交，不能用最后写入静默覆盖其他成员的修改。

每次修改记录编辑者、字段、修改前后版本、时间、IP、User-Agent 和请求 ID。为支持共同编辑追责和误操作恢复，建议使用内容修订表保留字段原文；修订记录只对宿舍成员及有范围权限的内容管理员开放，一期可以不提供用户侧历史界面。

### 6.3 Markdown

简介和公约沿用树洞正文的安全 Markdown 管线：

- 支持 CommonMark、表格和删除线；普通换行按换行显示；
- 原始 HTML 和 Markdown 图片不渲染；
- 服务端关闭原始 HTML，渲染后再使用 `nh3` 按标签、属性和协议白名单清洗；
- 链接只允许 `http`、`https`、`mailto`，并添加 `noopener noreferrer nofollow`；
- 数据库保存 Markdown 原文，详情接口额外返回清洗后的 HTML；
- 前端只能把服务端返回的清洗后 HTML 插入内容区域，不得自行解析原文；
- 预览调用受认证的服务端接口，并使用与保存后详情完全相同的渲染函数。

宿舍编号、昵称、成员姓名和所有卡片字段始终按纯文本转义，不能作为 Markdown 或 HTML 渲染。

### 6.4 成员卡片

- 成员按“宿舍长优先，其余按导入顺序”展示。
- 宿舍长卡片使用更深的同性色系、星星图标和“宿舍长”标识，不能只依靠颜色表达身份。
- 自己的卡片继续显示“我的卡片”标识；可以沿用现有卡片详情与编辑入口。
- 衣服尺码不得出现在宿舍接口、宿舍页面或其他成员详情中。
- 自己宿舍中的成员即使尚未发布卡片，也展示由正式账号提供的姓名、年级、专业和“尚未发布卡片”占位；不虚构卡片内容。
- 点击已发布卡片时复用现有卡片详情规则。卡片被隐藏后只显示不可用状态。

### 6.5 转让宿舍长

- 只有当前宿舍长可以发起转让；目标必须是同一宿舍中关联到有效普通账号的其他成员。
- 前端要求二次确认，并明确转让后原宿舍长立即失去转让权限。
- 后端在一个事务中串行检查宿舍成员关系，先校验当前操作者仍为宿舍长，再完成角色交换。
- 转让不能造成零名或多名宿舍长；数据库增加“每宿舍最多一名宿舍长”的唯一约束，事务负责保证至少一名。
- 操作写入审计日志。并发转让中最多一个成功，其余返回 `409`。

## 7. 赛博串门

### 7.1 列表

- 默认只展示未被管理员隐藏的正式宿舍，自己的宿舍置顶并标识“我的宿舍”。
- 首次加载 15 个宿舍，点击“查看更多”后每次再加载 15 个，不能一次返回全部宿舍及完整成员卡片。
- 支持按宿舍编号、宿舍昵称或成员姓名搜索；姓名搜索由后端完成，并且只在当前用户有权看到的成员范围内匹配。
- 列表卡片展示组合名称、简介纯文本摘要、可见成员头像和成员数量。列表不返回完整公约或完整卡片详情。
- 排序固定为“自己的宿舍优先、最近更新倒序、ID 倒序”，分页游标包含稳定排序字段，避免更新时重复或漏页。

### 7.2 查看其他宿舍

- 访客可以查看组合名称、简介、公约，以及其本来有权查看的已发布成员卡片。
- 访客不能看到未发布、已隐藏或因拉黑关系不可见的卡片内容；对应位置显示不包含姓名和头像的“成员信息暂不可见”占位。
- 任一方拉黑后，双方不能通过宿舍页面重新获取对方卡片或用成员姓名搜索到对方。
- 宿舍页面不得返回成员登录标识、账号状态、内部用户 ID、衣服尺码、私信内容或管理员信息。
- 访客页面不渲染编辑、成员纠错、转让宿舍长等按钮；后端仍必须拒绝直接调用写接口。

“赛博串门”展示的是内部社区信息，不对未登录访客开放，也不应被搜索引擎索引。页面响应设置 `Cache-Control: private, no-store`；前端路由页面增加 `noindex` 语义。

## 8. 后花园预留

一期只显示“后花园 · 建设中”的入口标识，不接收用户填写的 URL，不进行跳转，也不为每个宿舍创建目录或 HTML 文件。

后续实现时建议复用现有静态内容构建机制，通过受版本控制的内容清单把稳定的正式宿舍 ID 映射到静态页面 slug。不能直接把宿舍编号或用户输入拼接为文件路径，也不能允许任意外链作为“后花园”。该功能需要单独设计发布权限、构建失败回滚和内容审核。

## 9. 权限与管理范围

正式宿舍权限必须加入后端固定白名单，并同步更新《身份权限设计》。不能复用选宿舍阶段的 `DORMITORY_*` 权限，以免普通管理员借正式宿舍入口修改选宿舍结果，或反向越权。

建议新增：

| 权限编码 | 能力 | 数据范围 |
|---|---|---|
| `OFFICIAL_DORMITORY_READ` | 在管理端查看正式宿舍、成员及修订记录 | `management_grade_id` |
| `OFFICIAL_DORMITORY_IMPORT` | 预检并导入正式宿舍名单 | 文件中每个宿舍的 `management_grade_id` |
| `OFFICIAL_DORMITORY_MEMBER_UPDATE` | 纠正正式成员和宿舍长 | 原宿舍管理年级；改变年级时还需覆盖新年级 |
| `OFFICIAL_DORMITORY_MODERATE` | 隐藏、恢复或重置昵称、简介和公约 | `management_grade_id` |

规则如下：

- 至少一个有效管理员组必须同时包含所需权限并覆盖目标年级，不能拼接不同组的权限和范围。
- 批量预检可以逐行显示错误；确认导入必须整批授权并整批提交。
- 超级管理员直接通过权限层，但仍不能绕过文件哈希、成员账号、人数、同年级、唯一宿舍长、确认和审计约束。
- 永久删除正式宿舍只允许超级管理员；普通内容管理员只能隐藏或恢复内容。
- 无管理权限的宿舍成员仍可依据成员关系共同编辑自己宿舍的三个内容字段，这属于资源级权限，不是管理权限。
- 权限、管理员组或范围被撤销后，下一次请求立即失效；权限不能写入 Access Token 或长期缓存。

## 10. 内容治理、账号状态与数据保留

### 10.1 内容治理

- 昵称、简介和公约分别具有 `NORMAL`、`HIDDEN` 状态，避免处理一个违规字段时隐藏整个宿舍。
- 管理员隐藏、恢复或重置内容必须填写原因。被隐藏字段对成员和访客显示统一占位；有范围权限的管理员仍可查看原文以便治理。
- 宿舍成员修改已隐藏字段不能自动恢复可见性；只有内容管理员可以恢复。
- 一期不开放宿舍内容举报入口。若后续增加举报，应扩展现有举报目标类型并保存必要快照，不能把完整成员资料写入举报记录。

### 10.2 账号状态

- `SUSPENDED` 或 `BANNED` 成员仍保留在正式名单中，但不能登录、编辑或转让宿舍长身份。
- 登录标识批量修改不影响成员关系，因为正式成员通过内部用户 ID 关联；导入时使用的原登录标识只作为审计信息，不在学生端展示。
- 姓名、年级和专业变更后，页面默认展示当前账号字段；管理范围仍使用正式宿舍固定的 `management_grade_id`，避免修改用户年级导致宿舍授权漂移。
- 永久删除账号时，成员行的用户外键置空并保留导入时的最小身份快照，学生端显示“已删除账号”。若被删除者是宿舍长，事务把身份转给导入顺序最靠前的其他有效成员；没有可用成员时保留宿舍并标记“宿舍长待管理员处理”。

### 10.3 数据保留

- 账号停用、封禁、登录标识修改或卡片隐藏均不删除正式宿舍和共同内容。
- 正式宿舍内容、成员关系、修订和审计随常规 SQLite 备份保存，并纳入恢复演练。
- 删除误导入宿舍时，主体和成员可删除，但审计日志必须保留；如有内容修订，按生产数据清理策略保留必要审计元数据，不在日志复制完整正文。

## 11. 数据模型建议

### 11.1 `official_dormitories`

建议字段：

- `id`
- `dormitory_code`：全局唯一、管理员导入后不可由成员修改
- `nickname`
- `nickname_status`
- `description_markdown`
- `description_status`
- `rules_markdown`
- `rules_status`
- `management_grade_id`
- `version`：共同编辑乐观锁版本
- `created_by`、`created_at`、`updated_at`

建议索引：唯一 `dormitory_code`；列表分页 `(updated_at, id)`；管理范围 `(management_grade_id, id)`。不要给表名使用 `dormitories`，避免与组队宿舍混淆。

### 11.2 `official_dormitory_members`

建议字段：

- `official_dormitory_id`
- `user_id`：可空，账号永久删除时 `ON DELETE SET NULL`
- `role`：`LEADER` 或 `MEMBER`
- `position`：导入顺序 1–4
- `imported_login_identifier`：只供受权管理和审计，不返回学生端
- `name_snapshot`、`grade_snapshot`、`major_snapshot`：源账号删除后使用
- `created_at`

约束：同一宿舍 `position` 唯一；非空 `user_id` 在同一宿舍唯一；每宿舍最多一个 `LEADER` 的部分唯一索引；`position` 为 1–4。一个 `user_id` 可以出现在多个正式宿舍，不能建立全表唯一约束。

### 11.3 `official_dormitory_revisions`

建议字段：

- `id`
- `official_dormitory_id`
- `field_name`：`NICKNAME`、`DESCRIPTION`、`RULES`
- `previous_value`、`new_value`
- `from_version`、`to_version`
- `edited_by`
- `created_at`

该表用于处理共同编辑冲突、误操作恢复和治理追责。它不是公开动态流，访客接口不得读取。

### 11.4 审计

沿用现有审计表，新增导入确认、成员纠错、宿舍长转让、内容隐藏/恢复/重置和永久删除动作。记录操作者、命中的授权组、权限、范围、目标、原因、请求 ID、IP、User-Agent、结果和变更摘要；批量导入记录文件哈希与计数，不保存整个工作簿或账号密码。

## 12. API 边界建议

### 12.1 学生端

- `GET /api/official-dormitories/mine`：返回当前用户所属宿舍的轻量列表。
- `GET /api/official-dormitories`：分页和搜索可串门宿舍，只返回列表摘要。
- `GET /api/official-dormitories/{id}`：按成员/访客规则返回详情和可见卡片。
- `PATCH /api/official-dormitories/{id}`：成员更新昵称、简介或公约，要求 `version`。
- `POST /api/official-dormitories/markdown/preview`：成员预览简介或公约 Markdown。
- `POST /api/official-dormitories/{id}/leader-transfer`：宿舍长转让身份。

接口请求和响应统一使用现有命名约定。详情中的成员使用专门的最小 DTO，不直接复用包含受限字段的管理员用户或完整卡片对象。

### 12.2 管理端

- `POST /api/admin/official-dormitories/import/preview`：解析文件、校验权限并返回哈希和预检结果。
- `POST /api/admin/official-dormitories/import/confirm`：重新接收文件和预期哈希，原子导入。
- `GET /api/admin/official-dormitories`：按授权年级分页、按编号或成员姓名搜索。
- `GET /api/admin/official-dormitories/{id}`：读取正式宿舍、成员和必要修订信息。
- `PUT /api/admin/official-dormitories/{id}/members`：完整替换成员顺序并纠错，要求原因和版本。
- `POST /api/admin/official-dormitories/{id}/content-moderation`：隐藏、恢复或重置指定字段。
- `DELETE /api/admin/official-dormitories/{id}`：超级管理员确认后删除误导入宿舍。
- `POST /api/admin/official-dormitories/batch-delete`：超级管理员确认后，在单个事务内批量删除所选误导入宿舍。

访问无权资源时，学生端和范围受限的管理详情统一返回 `404`，避免枚举宿舍和成员关系；明确拥有资源但状态不允许写入时返回 `409`。

## 13. 安全、性能与可靠性

### 13.1 输入与输出

- 所有 Markdown 由服务端渲染和清洗；所有其他用户输入进行长度、字符和纯文本校验。
- Excel 解析器不得执行公式、宏、外链或嵌入对象；导出的错误报告对以 `= + - @` 开头的值进行公式注入转义。
- 解析前检查工作簿 ZIP 结构：条目不超过 1000 个、总解压体积不超过 20 MiB，并拒绝加密条目、宏、外部关系、DTD/实体及图片或 OLE 等嵌入内容，避免压缩炸弹和 XML 实体攻击。
- 文件解析异常统一返回受控错误，不把堆栈、数据库语句或服务器路径返回前端。
- 学生端 DTO 使用字段白名单，禁止通过 ORM 自动序列化泄露登录标识、内部 ID、衣服尺码或管理字段。
- 所有写接口继续使用现有 Cookie、Access/Refresh Token 和 CSRF 防护。

### 13.2 限流建议

| 操作 | 用户限制 | IP 限制 |
|---|---:|---:|
| 列表和详情 | 120 次/分钟 | 600 次/分钟 |
| Markdown 预览 | 30 次/分钟 | 120 次/分钟 |
| 共同内容修改 | 20 次/分钟 | 100 次/分钟 |
| 宿舍长转让 | 5 次/10 分钟 | 30 次/10 分钟 |
| 导入预检 | 10 次/10 分钟 | 30 次/10 分钟 |
| 导入确认或成员纠错 | 5 次/10 分钟 | 20 次/10 分钟 |

限流键同时包含已认证用户与来源 IP，不能只依赖前端按钮禁用。命中限制返回 `429` 和稳定错误编码。

### 13.3 查询与分页

- 列表查询先分页正式宿舍，再批量查询当前页成员和卡片，禁止每个宿舍单独执行成员查询。
- 列表只返回摘要和缩略字段；详情按需读取完整 Markdown 与卡片。
- 搜索成员姓名使用索引友好的关系查询，并受可见性和拉黑条件约束；至少设置最大搜索长度。
- 不把 Base64 头像写入响应或数据库；继续使用外置头像 URL 和已有失败恢复策略。
- 目标规模按 2000 个正式宿舍、8000 条成员关系和 100 个并发访问者验收。

### 13.4 缓存与并发

- 个性化成员可见性、拉黑关系和“我的宿舍”响应不得使用共享公共缓存。
- 清洗后的 Markdown 可以按内容版本做请求内或受控缓存，内容变更和治理状态变化后必须失效。
- 昵称/正文修改使用 `version` 乐观锁；宿舍长转让、成员纠错和导入使用事务和数据库约束。
- 所有失败事务完整回滚，不留下没有成员、没有管理年级或多名宿舍长的正式宿舍。

## 14. 可访问性与前端细节

- 宿舍长身份同时使用图标和文字，不只使用颜色；男女卡片颜色继续沿用粉色/蓝色主题，并保证文字对比度。
- 卡片和详情可使用键盘打开，切换器、弹窗和确认按钮具有可读标签和焦点管理。
- Markdown 表格在移动端允许内容区域横向滚动，不能撑宽整个页面。
- 加载更多按钮显示加载中并防止重复点击；请求失败保留已有列表并允许重试。
- 编辑冲突时保留未提交文本，不能因刷新弹窗丢失用户输入。
- 页面在 390 px 移动端宽度下不产生整页横向滚动。

## 15. 验收标准

### 15.1 导入与数据隔离

- 合法 `.xlsx` 可以预检并原子导入，第一位成员成为唯一宿舍长。
- 错误账号、重复编号、跳列、超员、跨年级、越权或文件哈希变化均被拒绝且不产生部分数据。
- 相同文件重复确认只跳过完全一致的宿舍；相同编号但不同成员不能静默覆盖。
- 正式宿舍数据不会修改组队宿舍、选宿舍轮次或历史快照。
- 同一学生可以属于多个正式宿舍，并能在“我的宿舍”正确切换。

### 15.2 学生功能

- 成员可以修改自己宿舍的昵称、简介和公约，非成员直接调用写接口失败。
- 两名成员并发编辑时不会静默覆盖；旧版本提交返回 `409`。
- Markdown 的标题、列表、引用、表格、代码、删除线和安全链接正确展示；脚本、原始 HTML、图片和危险协议不能形成可执行节点或外部请求。
- 只有当前宿舍长可以向有效舍友转让身份，并发转让后仍恰好一名宿舍长。
- 无宿舍、多宿舍、未发布卡片、隐藏卡片、账号删除占位和宿舍长待处理状态都有明确页面表现。

### 15.3 串门、隐私与权限

- 未登录访问重定向登录；已登录用户可分页浏览和按编号、昵称或可见成员姓名搜索。
- 访客不能修改其他宿舍，也不能读取未发布、已隐藏、被拉黑成员的资料。
- 学生端响应不存在登录标识、账号状态、衣服尺码、私信、管理权限和不必要的内部用户 ID。
- 普通管理员只能读取或操作某一个有效管理员组同时覆盖权限与管理年级的正式宿舍。
- 停用组、移除权限或缩小范围后，下一次请求立即失效。
- 导入、成员纠错、宿舍长转让、治理和删除均产生完整但不复制敏感正文的审计记录。

### 15.4 性能与上线

- 列表每次最多返回 15 个宿舍，成员和卡片使用批量加载，不出现按宿舍增长的 N+1 查询。
- 在目标数据量和 100 个并发访问者下，列表与详情无不可解释的数量级性能回退，容器并发保护和资源限制仍生效。
- Ruff、后端测试、Alembic 升级与一致性检查、JavaScript 语法检查、浏览器验收、Docker 构建和健康检查全部通过。
- Alembic 在生产数据库副本上可升级；备份恢复演练能够恢复正式宿舍、成员、修订和审计数据。
- SonarCloud 为 `0 New issues`、`0 Security Hotspots` 后方可合并。
